yt-slidesnap — लेक्चर वीडियो को उसकी स्लाइड्स के PDF में बदलें

2026-10-10  ·  साइट देखें

English · हिंदी

यह क्या है

एक Python CLI (और एक छोटा लोकल वेब UI) जो एक वीडियो URL और उन टाइमस्टैम्प के साथ लिया जाता है जहाँ स्लाइड्स दिखती हैं, और हर पेज पर एक स्लाइड वाला साफ़ PDF लौटाता है। यह वीडियो डाउनलोड नहीं करता — स्ट्रीम रिज़ॉल्व करता है और सिर्फ़ ज़रूरी फ़्रेम निकालता है।

बनाया गया एक ख़ास उबाऊ काम के लिए: ढाई घंटे की रिकॉर्डेड क्लास जिसमें 40 सवाल हों, और आपको टाइमलाइन हाथ से स्क्रब करने के बजाय सवालों की स्लाइड्स एक दस्तावेज़ में चाहिए। हर पेज पर कैप्शन ([Q22 at 1:34:21]) आता है और टूल साफ़-साफ़ छापता है कि उसने आपके टाइमस्टैम्प कैसे पढ़े — यानी ग़लत पढ़ा गया तो log में दिखेगा, चुपचाप PDF में नहीं।

यह क्यों मायने रखता है

दिलचस्प हिस्सा PDF नहीं है — यह है कि फ़्रेम बिना किसी ML के साफ़ कैसे निकलते हैं।

किसी टाइमस्टैम्प पर सीधे फ़्रेम उठाने से आमतौर पर स्लाइड के सामने खड़ा प्रेज़ेंटर कैद हो जाता है। यहाँ हल एक सांख्यिकीय तरकीब है जिसकी लागत शून्य है:

  • हर स्लाइड विंडो से एक ही ffmpeg पास में 8 बार सैंपल लिया जाता है।
  • आठों फ़्रेम stack किए जाते हैं और per-pixel median निकाला जाता है।
  • स्लाइड स्थिर है; प्रेज़ेंटर नहीं। तो median वह स्लाइड है जिसमें से प्रेज़ेंटर मिट चुका है।
  • उस median के सबसे क़रीब वाला candidate (सबसे कम mean absolute deviation) वह फ़्रेम है जिसमें वे उसे सबसे कम ढकते हैं।

न मशीन लर्निंग, न फ़ेस डिटेक्शन — बस stack पर numpy.median। यही पूरा विचार है, और यह किसी भी "स्थिर बैकग्राउंड से हिलती चीज़ हटाओ" समस्या के लिए सचमुच दोबारा इस्तेमाल लायक पैटर्न है।

दो और डिज़ाइन फ़ैसले चुराने लायक हैं:

  • सैंपलिंग अगली row नहीं, बल्कि सबसे पहले आने वाले बाद के टाइमस्टैम्प तक सीमित है। पार्सर में min(later) का मतलब है कि विंडो कभी जवाब के दिखने से आगे नहीं बढ़ सकती, यानी जवाब PDF में लीक नहीं हो सकता और विंडो अगले सवाल पर नहीं सरक सकती। एक नकारात्मक शर्त जो उम्मीद पर नहीं, गणित पर टिकी है।
  • हर candidate फ़्रेम सहेजा जाता है, इसलिए फिर से चुनना मुफ़्त है — --override Q22=5 किसी एक candidate को बिना दोबारा extraction पिन कर देता है।

इस्तेमाल कैसे करें

इंस्टॉल

pipx install git+https://github.com/pavnxet/yt-slidesnap   # yt-slidesnap कमांड देता है
# या
pip install git+https://github.com/pavnxet/yt-slidesnap

clone से करना हो: pip install -r requirements.txt, फिर python slidesnap.py ... चलाएँ — उस रास्ते पर yt-slidesnap कमांड मौजूद नहीं होता, जब तक pip install -e . न चलाएँ। README इसे सबसे आम गड़बड़ बताता है।

आपको ffmpeg इंस्टॉल करने की ज़रूरत नहीं। पूरा build imageio-ffmpeg के अंदर आता है और टूल हमेशा वही इस्तेमाल करता है (FFMPEG = imageio_ffmpeg.get_ffmpeg_exe()). स्ट्रीम yt-dlp रिज़ॉल्व करता है।

चलाएँ

टाइमस्टैम्प लगभग जैसे आपके पास पहले से हैं, वैसे ही चिपका सकते हैं:

Q22: Question 01:34:21 | Answer 01:34:53 (C)
Q23: Question 01:38:45 | Answer 01:39:16 (D)

Markdown tables भी चलती हैं, जिनमें एक row में कई बाद के टाइमस्टैम्प हों। फिर:

yt-slidesnap run "<video-url>" --file timestamps.txt
yt-slidesnap run "<video-url>" --text "Q22: Question 01:34:21 | Answer 01:34:53 (C)"
cat timestamps.txt | yt-slidesnap run "<video-url>"

पूरा run ख़र्च करने से पहले जाँचें:

yt-slidesnap run "<url>" --file timestamps.txt --dry-run

यह पढ़ी गई विंडो छापकर (Q19 1:41:04 -> 1:41:27 23s) बिना extraction बाहर निकल जाता है। हर असली extraction भी वही विंडो छापता है जो उसने समझी।

वेब UI

yt-slidesnap serve      # http://127.0.0.1:8765 खोलता है

URL और टाइमस्टैम्प चिपकाएँ, Extract दबाएँ, प्रोग्रेस देखें, फिर PDF लिंक और contact-sheet प्रीव्यू मिलता है। डिफ़ॉल्ट रूप से 127.0.0.1 पर बँधता है; एक बार में एक ही run (दूसरा क्लिक 409 के साथ रिजेक्ट होता है, क़तार में नहीं लगता)।

सीमाएँ और जोखिम

  • YouTube पर आउटपुट 640×360 तक सीमित है, और यह बग नहीं, सख़्त बाधा है। README और कोड की टिप्पणी दोनों बताते हैं कि YouTube का android client ही अकेला ऐसा है जो ffmpeg को असल में फ़ेच होने लायक URL देता है, और वह client 360p पर रुक जाता है। इससे ऊपर जाने के लिए yt-dlp की nsig हैंडलिंग के लिए JS runtime चाहिए, और फिर भी उस client का URL HTTP 403 दे सकता है (स्ट्रीम URL उसी client से बँधा होता है जिसने माँगा)। PDF लिखते समय टूल 2× upscale करता है। स्लाइड के टेक्स्ट के लिए ठीक; छोटे लेबल वाले diagram के लिए नहीं।
  • यह किसी और के वीडियो के फ़्रेम डाउनलोड करता है। README यह साफ़ कहता है: पढ़ाई के नोट्स और fair-use quotation के लिए ठीक, लेक्चर दोबारा प्रकाशित करने के लिए नहीं। आउटपुट फ़ोल्डर डिफ़ॉल्ट से gitignored है — ऐसा ही रखें, और कुछ भी साझा करने से पहले प्लेटफ़ॉर्म की शर्तें और वीडियो के मालिक का हक़ देखें। यही सबसे ज़रूरी बात है; टूल यह आपके लिए लागू नहीं कर सकता।
  • Age-restricted या members-only वीडियो के लिए cookies एक्सपोर्ट करके yt-dlp को देने पड़ते हैं, वरना स्ट्रीम रिज़ॉल्व ही नहीं होगा (could not resolve a stream URL)।
  • प्रति टाइमस्टैम्प एक फ़्रेम। अगर स्लाइड animation से बनती है, तो जो उस पल स्क्रीन पर है वही मिलेगा — "पूरी बनी स्लाइड ढूँढो" जैसा कोई तर्क नहीं है।
  • Median तरकीब तब फेल होती है जब विंडो के अंदर स्लाइड ख़ुद बदल जाए। तब median दो स्लाइड्स का मिश्रण बनता है और हर candidate ख़राब स्कोर करता है। यह चुपचाप नहीं, पकड़ में आता है: error X vs worst Y वाला आउटपुट इसे दिखाता है — अगर X और Y क़रीब हैं तो सभी candidates गंदे थे और --frames बढ़ाना चाहिए। कम भरोसे वाले pick पर आँख बंद कर भरोसा करना ही असली फेलियर है।
  • सिर्फ़ YouTube अंत से अंत तक टेस्टेड है, हालाँकि यह हर उस चीज़ पर चलता है जिसे yt-dlp सपोर्ट करता है।
  • वेब UI में कोई ऑथेंटिकेशन नहीं। यह सिर्फ़ मौजूदा run का आउटपुट फ़ोल्डर सर्व करता है, बनावट से सिंगल-यूज़र है, और loopback पर बँधता है। इसे ऐसे नेटवर्क पर न खोलें जिस पर भरोसा न हो — साझा नेटवर्क पर --host 0.0.0.0 आपके निकाले फ़्रेम सबको दे देगा। दूसरे क्लिक पर 409 का मतलब है क़तार नहीं, यानी यह कई यूज़र के लिए नहीं बना।
  • रफ़्तार का आँकड़ा ख़ुद बताया हुआ दावा है। "16 slides in ~25 seconds" प्रोजेक्ट के अपने README से है और यहाँ स्वतंत्र रूप से नापा नहीं गया। इसे संकेत मानें, बेंचमार्क नहीं।

निष्कर्ष

छोटा, साफ़-सीमा वाला, और एक उपयोगिता के लिए असामान्य रूप से अच्छी तरह तर्क दिया हुआ — ऐसा टूल जिसका README बताता है कि क्यों काम करता है, सिर्फ़ क्या टाइप करना है नहीं।

इसके लिए इस्तेमाल करें: रिकॉर्ड किए गए लेक्चर या वेबिनार को खोजने और टिप्पणी करने लायक स्लाइड दस्तावेज़ में बदलने के लिए, परीक्षा-रिवीज़न रिकॉर्डिंग से सवालों की स्लाइड्स निकालने के लिए, और स्थिर दृश्य से हिलते व्यक्ति को हटाने वाली median तरकीब के संदर्भ कार्यान्वयन के तौर पर।

इसके लिए न करें: किसी और का लेक्चर दोबारा प्रकाशित करना, 360p से बेहतर बारीक़ी चाहने वाला कुछ भी, या ऐसी animated slides जहाँ आपको स्लाइड की पूरी बनी हालत चाहिए।

ईमानदार ढाँचा: क़ीमत कोड की मात्रा में नहीं, दो फ़ैसलों में है — per-pixel median (बिना ML साफ़ फ़्रेम) और earliest-ceiling विंडो नियम (जवाब बनावट से लीक नहीं हो सकते)। दोनों ऐसी चीज़ें हैं जो पीछे से देखकर साफ़ लगती हैं और ग़लत करना आसान है, और टूल की अपनी logging (error X vs worst Y, छपी हुई विंडो) ही ग़लत मामलों को चुपचाप होने के बजाय दिखने लायक बनाती है।
