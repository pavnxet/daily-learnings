# Architecture Decision Records — daily-learnings

## ADR-001: One file per tool instead of one growing README

- **Date**: 2026-10-10
- **Status**: Accepted
- **Context**: Daily entries accumulate. A single README would grow into an unnavigable document and make every new entry a merge conflict.
- **Decision**: One markdown file per tool in `tools/<slug>.md`, with a one-row index in `README.md`.
- **Consequences**: Adding a tool touches two files (entry + index row). In return, entries stay independently readable and diffable, and a broken entry cannot corrupt the rest of the log.

## ADR-002: No site generator, no build step

- **Date**: 2026-10-10
- **Status**: **Superseded by ADR-004** (the user asked for a GitHub Pages website)
- **Context**: The repo is read on GitHub and by agents as plain text.
- **Decision**: Plain markdown only. No Jekyll/Hugo/Astro, no CI, no dependencies.
- **Consequences**: Nothing to maintain or debug; zero tooling cost. Cost: no search, tags, or themes — acceptable until the log is large enough to need an index, which the README table already provides.

## ADR-003: Mark unverified vendor claims inline

- **Date**: 2026-10-10
- **Status**: Accepted
- **Context**: Tool research relies heavily on vendor marketing pages. Pasted-at-face-value marketing ages into misinformation, and a future reader cannot tell which lines were tested.
- **Decision**: Tag vendor-sourced figures `(vendor claim — unverified)` in the entry text, and keep a separate "Limits & risks" section.
- **Consequences**: Entries read slightly less cleanly, but every number carries its provenance and can be re-verified or deleted with confidence.
- **Follow-up (2026-10-10)**: the tag must be written **inline at the number**, not as one blanket note per section. The first draft used a single `*(All figures … vendor claims — unverified.)*` line, and the generator's `vendor claim` matcher silently skipped it (plural "claims"). Inline tags are also what the site highlights.

## ADR-004: Publish GitHub Pages from `docs/`, generated by a script

- **Date**: 2026-10-10
- **Status**: Accepted
- **Context**: The user wanted a website on GitHub Pages. GitHub Pages serves `.md` files as **plain text**, not rendered HTML, so the option of linking the site straight at `tools/*.md` produces raw markdown in the browser. The alternatives were Jekyll (Pages' default, adds config/build machinery) or a static-site framework (heavy dependency).
- **Decision**: `tools/*.md` stays the source of truth. A single dependency-free `generate.py` converts each entry to `docs/tools/<slug>.html` and rebuilds `docs/index.html`. Pages is configured as `main` / `docs`, with `docs/.nojekyll` to switch Jekyll off.
- **Consequences**: One ~30-line markdown subset to maintain, covering only the constructs entries actually use (headings, tables, fenced code, lists, quotes, links, bold/italic/code). Adding an exotic markdown feature means extending the converter. Benefit: the writing format and the published site cannot drift apart, and there is no build dependency or CI to break.

## ADR-005: The site index is generated from entry metadata, not hand-maintained

- **Date**: 2026-10-10
- **Status**: Accepted
- **Context**: A website needs an index. A hand-written `docs/index.html` would need editing for every new entry, and would silently go stale.
- **Decision**: `generate.py` reads each entry's `**Summary**` and `**Logged**` metadata lines and builds the card index itself, newest first. Entries missing `**Logged**` fall back to `DEFAULT_DATE`.
- **Consequences**: A new entry appears on the site by existing and running the generator — no HTML editing. Cost: the metadata block's key names are a real contract (see AGENTS.md) and must not be renamed casually. The README index table stays hand-maintained, since it doubles as the repo's human summary.

## ADR-006: `vendor claim` tags are highlighted with `<strong>`, not a custom highlight style

- **Date**: 2026-10-10
- **Status**: Accepted
- **Context**: An early draft rendered the unverified-claim tag through a `mark` rule with a theme colour variable.
- **Decision**: Use `<strong>`, dropping the `mark` rule and its `--mark` variable.
- **Consequences**: One less style rule and one less colour variable, and the warning reads correctly in both light and dark mode for free. It also stays legible if the CSS is ever stripped (e.g. RSS or reader mode).
